# S3-only version protection and retirement

The approved phase-two implementation for [#24](https://github.com/CraigDevJohnson/minecraft/issues/24) uses the exact-version receipt foundations and `lifecycle_mode = "s3-only"`. Local implementation does not authorize activation, live IAM changes, disk removal or retirement. The later lifecycle/data-volume migration must include its concrete saved plan and recurring policy. Keep the existing deployment and verified recovery points until that migration passes. No new service, Object Lock configuration, scheduler or permanent version-deletion role is introduced.

## Protection and bounded ownership

Use one per-version tag, `minecraft-retention=keep|retired`, in the existing versioned backup bucket. Only versions explicitly marked `retired` are eligible for expiration. Untagged candidates and `keep` versions have no age-only expiration. Replace the existing blanket 14-day noncurrent-version expiration for the S3-only instance prefixes; do not leave another lifecycle rule that can expire kept versions. S3 supports [lifecycle filters combining a prefix and tags](https://docs.aws.amazon.com/AmazonS3/latest/userguide/intro-lifecycle-filters.html), and [tagging a specific object version](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObjectTagging.html).

Retain the latest 14 independently verified completed recovery points per instance, plus the authoritative selection and any point referenced by an active or interrupted operation. The selection is always retained even if it falls outside the catalog order. Each retained point owns one exact marker version and archive version; receipt-backed points also retain their immutable receipt version. Earlier points use the [reviewed legacy recovery-point import](s3-only-legacy-import.md), which records their exact source/content evidence without fabricating a final-session receipt. Preserve the corresponding last 14 selection versions as small audit records. More recent conflicting versions do not replace those selected versions. The private journal records the finite keep set, object-version identities, proposed retirements and readback before any destructive step.

Enforce immutable publication for point archives, completed markers and immutable receipt keys using `If-None-Match: *`. Use `If-Match` only for the authoritative `receipts/current.json` selection. Bucket policies can [enforce these conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes-enforce.html); multipart creation and parts need the documented `s3:ObjectCreationOperation` exemption. This prevents ordinary retries from creating unnecessary body versions. Selection publication remains idempotent and serialized by the designated workstation lock.

The S3-only runtime role cannot delete current backup objects, delete versions, change tags, write receipt selections or manage bucket lifecycle. It publishes immutable session backups and reads the selected recovery data. The existing retained-disk mode keeps its current pruning behavior. Move S3-only retirement to the approved operator controller so a stale host cannot remove a selected point or make it expire.

## Scoped permission changes

The saved plan must update both identity policies and any applicable permissions boundary. An identity-policy addition alone does not establish effective access.

The mode-specific infrastructure policy gives the host current/historical reads and immutable point publication only in configured completed/object prefixes, with receipt reads kept separate. Bucket denies also prevent that runtime principal from deleting objects or versions, changing tags, or writing receipts. All principals are denied direct recovery-version deletion and deletion of `receipts/current.json`; lifecycle owns physical retirement. Existing modes retain their earlier policy and lifecycle behavior.

Bucket deletion denies do not prevent S3's own lifecycle actions. The [AWS bucket-policy documentation](https://docs.aws.amazon.com/AmazonS3/latest/userguide/bucket-policies.html) makes that distinction explicit. Selected `keep` versions and untagged versions survive because every data-expiration rule requires the exact `retired` tag, with no competing blanket noncurrent expiration. Tag protection and readback are therefore required before removing the live disk; a deny statement alone cannot protect the only recovery copy from expiry.

The [host-boundary example](operator-role/host-boundary.json.example) adds only historical reads under instance recovery prefixes. The [operator retention supplement](operator-role/s3-only-retention.json.example) proposes exact-bucket/named-instance version listing, historical/tag reads, required single-key tag updates and conditional receipt publication. Its exact-bucket `s3:GetLifecycleConfiguration` permission lets the operator read the actual expiry rules before disk removal; [AWS documents this action for the lifecycle-read API](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetBucketLifecycleConfiguration.html). The runtime role does not need it. Replace the example bucket/instance with the reviewed deployment scope and merge only missing permissions into the administrator-owned operator policy and boundary where needed. It creates no profile or role and grants no permanent version deletion. Its tag conditions require a present, nonempty approved tag set; the bucket policy separately denies missing, invalid or extra retention tags even if another identity statement is broader. These examples require concrete review and effective-policy readback before activation.

| Principal | New or changed access | Resource scope |
| --- | --- | --- |
| Target runtime role | `s3:GetObjectVersion`, alongside existing current-key `s3:GetObject` | Exact deployment bucket and configured `instances/<id>/completed/*`, `objects/*`, and `receipts/*` prefixes |
| Operator controller | `s3:GetObjectVersion`, current/version tag reads and writes (`s3:GetObjectTagging`, `s3:GetObjectVersionTagging`, `s3:PutObjectTagging`, `s3:PutObjectVersionTagging`) | The same named-instance object prefixes, with the allowed retention tag key/value constrained |
| Operator controller | `s3:ListBucketVersions` and existing `s3:ListBucket` | Exact bucket ARN, conditioned on the configured named-instance prefixes |
| Operator controller | Immutable receipt `s3:PutObject` and conditional current-selection updates | `instances/<id>/receipts/*`, with separate conditions for immutable keys and `current.json` |
| Operator retirement step | Existing current-key `s3:DeleteObject`, only after verified retirement | Named-instance completed/object/obsolete receipt keys; no `s3:DeleteObjectVersion` |

`GetObjectVersion` is required by both HEAD and GET when a version ID is supplied; keep current-key reads because selection begins with the current key. Version tag reads/writes always include the exact version ID. Tag-write conditions must require the retention key with value `keep` or `retired`, rather than only allowing it when supplied; an empty replacement tag set must be denied. Unexpected preexisting object tags require investigation, rather than silently replacing another owner's metadata. Existing listing bounds and generic diagnostic errors still apply. Keep credentials temporary and private; verify the actual account before using them. There is no need to create a workstation profile merely to use a scoped temporary session.

Do not use object tags as the sole authorization guard for DELETE/overwrite; [S3 does not support existing-tag conditions for those operations](https://docs.aws.amazon.com/AmazonS3/latest/userguide/tagging-and-policies.html). Prevent runtime actions by principal/action/prefix policy, and explicitly deny current-key deletion of `receipts/current.json` to runtime and operator roles. The operator is the trusted actor allowed to advance selection and retire other data under the approved controller policy.

## Migration and session-end sequence

1. With the current disk retained, inventory all current and noncurrent marker/archive/receipt versions for the configured prefixes. Validate the selected point and the latest 14 completed points independently. Save a private inventory and rollback plan. Unexpected, conflicting or unreferenced versions remain protected for investigation.
2. Apply and read back the reviewed lifecycle and IAM change while the live disk remains available. Expiration must match only `retired`; retained and untagged versions must have no competing age-only expiration. Keep multipart-abort cleanup in a separate prefix-only rule. Keep expired-delete-marker cleanup separately because those actions cannot share a tag-filtered rule.
3. Drain the final session and verify its exact marker/archive and every checkpoint. Tag those versions and its immutable receipt `keep`, then read back their tags by version ID. Publish the conditional authoritative selection, tag/read back its exact new version, and durably save the same selection outside disposable resources. Any failed or uncertain readback retains the host/disk for repair.
4. Before the disk-deletion plan, verify the current selection again and prove that all its exact versions are in the keep set and excluded from expiration. Do not treat a replaced current S3 key or catalog `latest` as an alternative to a missing selected version.
5. Under that same workstation operation lock, derive retirement only from the complete verified inventory. Exclude the current selection, latest 14 valid points, all active/interrupted journal references and unclassified versions. Record exact eligible versions before tagging them `retired`; read back tags and reconcile interrupted retirement before advancing another lifecycle operation. Remove current discovery only for confirmed retired points.

Before each start, read back the authoritative selection, its tags and exact marker/archive versions. A selected version tagged `retired`, missing protection, conflicting local/S3 selection or incomplete retirement journal leaves the game stopped. Before each stop, reconcile the finite retirement backlog or report the concrete failure while preserving required recovery data.

## Expiry and failure limits

Configure current-object expiration and noncurrent-version expiration after 14 days only for `retired`. S3 expiration creates a delete marker for an eligible current version; noncurrent expiration permanently removes eligible historical versions. Expiration clocks are based on creation or when a version became noncurrent, not when a retention tag changed. An old already-noncurrent version may therefore become eligible immediately after retirement. Retirement must be treated as an irreversible approval-policy action, not a promised new 14-day grace period. [AWS lifecycle semantics](https://docs.aws.amazon.com/AmazonS3/latest/userguide/intro-lifecycle-rules.html) also require separate untagged rules for multipart abort and expired delete-marker cleanup.

The logical retained set is bounded to 14 points plus current/active exceptions; physical storage can temporarily exceed it while asynchronous lifecycle expiration processes the retired tail. It does not grow while the family server stays off. One tracked session and one serialized lifecycle operation limit unfinished captures; checksum-conflicting or unexplained objects block new destructive operations instead of being retired from age alone. A complete inventory that exceeds the configured scan/count bound requires an explicit repair plan. Do not disable expiration for all historical versions and leave ordinary cleanup without an owner.

Retirement does not repair a damaged catalog or permit deletion of the last known-good copy. If current selection verification, exact-version reads, tags, lifecycle readback, effective IAM, publication or journal reconciliation fail, preserve existing recovery data and disk resources. Failure to prove expiration or permission behavior cannot be represented as successful activation.

## Required proof before phase-two activation

Add credential-free policy/controller tests for selected noncurrent-version survival, more than 14 completed sessions with a bounded retained set, pointer overwrite/delete-marker scenarios, tag/readback failures, interrupted retirement, stale hosts, denied version deletion and conflicting lifecycle rules. Include a near-capacity restore and failed restore preserving target data. Then prove the same scoped reads, tag protection, retirement and S3-only round trip against the reviewed live bucket. Record no session EBS disks while off and startup time including the existing 15-minute fresh-disk provenance wait. These are #24 completion requirements, not evidence provided by the receipt-only PR.
