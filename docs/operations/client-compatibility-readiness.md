## NetherNet transition

[GeyserConfig at the commit reviewed on October 3](https://github.com/GeyserMC/Geyser/blob/63a4e2b79b12f0d138777d5fd80176a112b4bd72/core/src/main/java/org/geysermc/geyser/configuration/GeyserConfig.java) (`63a4e2b`, Geyser 2.11.3) defines `raknet`, `both` and `nethernet`. Since build 1280 only `both` and `nethernet` remain, as at the pinned `50360e3` (build 1288). The source identifies RakNet removal in Bedrock 26.60. With `both`, WebRTC needs a UDP port different from RakNet. Built-in signaling binds TCP, normally the Bedrock port. TLS takes a certificate/key or PKCS12 file; without it, clients get the first-use trust prompt. The external `nxs` option registers with another service and supports a private token.

The [NetherNet implementation at that commit](https://github.com/GeyserMC/Geyser/blob/63a4e2b79b12f0d138777d5fd80176a112b4bd72/core/src/main/java/org/geysermc/geyser/network/bedrock/nethernet/NetherNetServer.java) binds built-in TCP signaling and pins WebRTC to the selected UDP port. It stores a server identity under Geyser's data directory and reports failures when native WebRTC support is unavailable. ARM64 startup and real connectivity must therefore be tested rather than inferred from configuration parsing. Retain the identity through restart, backup and restore as part of plugin state.

Craig approved `both` during transition, with self-contained `builtin` signaling, RakNet UDP `19132`, signaling TCP `19132`, and WebRTC UDP `19133`. It avoids adding an external signaling account/service. The first-use trust prompt is approved; no TLS certificate or external signaling service is selected. Activation uses the concrete reviewed plan. Keep the generated built-in server identity private and retain it through backup/restore. Document address/port semantics from the selected release; household demonstrations are waived. The Crafty server applies this design on each start ([ADR 0008](../adr/0008-the-adapter-applies-the-pinned-server-content.md)), and [how players join](crafty.md#how-players-join) gives the address and port on each device type.

Implement config policy, manifest checksum, Compose port publication, infrastructure/recovery ingress, tests and transport-aware runtime validation together. A TCP HTTP response proves signaling only; a RakNet discovery ping proves only RakNet. Technical validation must establish the selected transport, supported protocols and external WebRTC reachability. A local native-channel result alone does not prove that external path. Household join demonstrations are waived and must not be reported as performed. Check whether the selected native library requires additional egress on the actual deployment before proposing a rule. The implementation adds initiated UDP egress to client-selected ports 1–65535 beside TCP 80/443; review this in the activation plan.

The [official Bedrock 26.50 changelog](https://feedback.minecraft.net/hc/en-us/articles/48826825649933-Minecraft-Bedrock-Edition-26-50-Changelog-Wilderness-Bound) says dedicated servers now default to NetherNet. It does not establish that this family's Geyser or console route passes 26.60. No official 26.60 release date or qualifying compatibility declaration was found in this check. That remains unknown; no speculative date belongs in the rollout plan.

## Optional console compatibility follow-up

[BedrockConnect](https://github.com/Pugmatt/BedrockConnect) redirects a featured-server connection to its server list, then transfers the client to the entered target. The inspected [release 1.71.0](https://github.com/Pugmatt/BedrockConnect/releases/tag/1.71.0), published September 15, declares 26.50 support. That metadata does not declare 26.60 support. If console play is pursued later, recheck the maintainer's release and transport guidance. List entry, DNS redirection or a successful tablet join does not establish console transport compatibility.
