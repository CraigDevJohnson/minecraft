# Instance allowlist changes

The family has one allowlist for every world: the allowlist of record, which the [launcher](launcher.md#allowlist-changes) keeps in the SSM parameter `/<resource_prefix>/launcher/allowlist` ([ADR 0009](../adr/0009-one-host-per-world.md)). From anywhere, add or remove a player on The Lobby's Minecraft Admin page (Members with `minecraft-admin`), with the [Server control workflow](cloud-controls.md#the-server-control-workflow) (`allowlist-add` or `allowlist-remove` with the edition and the name) or `task server:allowlist OP=add EDITION=java PLAYER=<name>`. All three ask the launcher, and none takes a world. The page also lists the record (`GET /server/allowlist`). The launcher looks the player up, changes the record, and runs the host command below on each world that is running. A stopped world needs nothing: every start writes the record over that world's `whitelist.json` before the game starts, so the record always wins over what a server or a restored archive held. A world that is starting has already read the list, so a change made then fails with `allowlist_failed`; the record keeps it, and asking again once that world is `ready` finishes it. The answer names the running worlds the change reached.

A change therefore works with every world stopped, and one change covers all three worlds. Removing a player also removes them from every world's operators, on the record and on each running world ([launcher](launcher.md#operators)). After the first Deploy the worlds are fresh and the record is empty: add each player once ([worlds](worlds.md#the-first-deploy)). The record is the only list to edit. A `whitelist add` typed into a world's console lasts until that world's next start.

## Linked accounts

A player with both a Java and a Bedrock account can play as one player on every world. Floodgate on each world uses GeyserMC's global linking, which is on by default and needs no setting, code or Deploy ([#104](https://github.com/CraigDevJohnson/minecraft/issues/104)). A linked Bedrock login joins with the Java account's UUID, name (no dot) and skin, so the Java entry's place on the allowlist, its operator status, its inventory and its land claims cover both editions, on all three worlds at once. Players with only one edition need nothing.

Linking moves nothing from the Bedrock identity to the Java one, and the launcher refuses to add or remove a gamertag once it is linked (`409 linked_account`). So the order matters:

1. **Move what matters off the Bedrock identity.** On each world where it has something: put its items and ender chest contents in chests, run `/flan list`, then stand in each claim and run `/flan transferClaim <JavaName>` (the Java account needs enough claim blocks), and empty any grave. Its player file stays on the world, out of reach while the link lasts.
2. **Remove the Bedrock entry** with every world stopped, on Minecraft Admin or with `allowlist-remove` and the `bedrock` edition, and check that the Java account is listed. This also takes the Bedrock identity off every world's operators. Left in place, the entry could no longer be removed once linked.
3. **Link** at [link.geysermc.org](https://link.geysermc.org/start): either sign in with the Bedrock account and then the Java account under "Online linking", or join the server `link.geysermc.org` on Java (port 25565) and on Bedrock (port 19132), run `/linkaccount` on one and `/linkaccount <code>` on the other within 15 minutes. On 2026-11-15 that server accepted Java 26.3 (protocol 777) and answered NetherNet signaling for Bedrock protocol 2225, the one our worlds report for Bedrock 26.60.
4. **Wait five minutes, then join a world on Bedrock.** GeyserMC keeps each lookup, "not linked" included, for about five minutes. The player should appear under the Java name, with the Java skin and inventory. The two editions can't be online at once: the newer login turns the older one away.

If GeyserMC's API does not answer when a linked player joins on Bedrock, Floodgate admits them as the old Bedrock identity, which the allowlist no longer holds, so they are turned away until it answers. `/unlinkaccount` on the link server undoes a link and brings the Bedrock identity, and everything it held, back; add its gamertag again to let it in.

## The host command

The rest of this page describes the host command, for the launcher's benefit and for a hands-on emergency.

The host command is the Crafty adapter's `allowlist` action. It needs the host's instance, which is its world's id, running with its Java port answering, holds the adapter's lifecycle lock, and refuses while the host is draining. The launcher installs the adapter it carries before it runs this command, so the host always has the version the launcher was deployed with ([ADR 0007](../adr/0007-the-launcher-carries-the-host-adapter.md)). The archive taken at the next stop includes `whitelist.json` with the rest of the server folder.

## The list a start carries

A start's `--allowlist-file` is a private regular file in `whitelist.json`'s own format: a JSON list of objects, each with exactly a canonical `uuid` and a `name` of 1 to 32 characters. The launcher writes it from the record, with a Java entry under the account's name and a Bedrock entry under the name Floodgate writes, a dot and the gamertag with its spaces as underscores. The adapter checks the file before anything changes and writes it over the stopped server's `whitelist.json`, owned like the file it replaces. A start without the flag leaves `whitelist.json` alone. Whether Floodgate admits a Bedrock player from an entry written this way is shown by the first Bedrock join of a player added while the world was stopped ([proof run](worlds.md#the-proof-run-for-a-world)); no test can show it.

## The live change

Provide one player's verified identity in a private JSON file owned by the user running the command, with mode `0600`. The object has `uuid` and `name` fields: use the actual server UUID in canonical lowercase hyphenated form, and the verified Java account name or unprefixed Bedrock gamertag. The file must refer to the same account in both fields. Identity verification remains required for each access change; test fixtures do not establish those identities. Craig resolved the console and family testing requirements on 2026-10-03; see the [current acceptance record](family-device-validation.md).

```sh
sudo /usr/local/sbin/minecraft-instance --config /etc/minecraft/operator.json allowlist survival add --edition java --player-file /private/java-player.json
sudo /usr/local/sbin/minecraft-instance --config /etc/minecraft/operator.json allowlist survival add --edition bedrock --player-file /private/bedrock-player.json
sudo /usr/local/sbin/minecraft-instance --config /etc/minecraft/operator.json allowlist survival remove --edition bedrock --player-file /private/bedrock-player.json
```

The adapter sends each console command through Crafty's API (`POST /api/v2/servers/<id>/stdin`), because the server has RCON off. Crafty writes every console command, with the name in it, to its audit log under `/srv/minecraft/crafty/` and to its container log under `/var/lib/docker`, both on the host's encrypted root disk, and the game writes the change to `logs/latest.log`. A removal by name also has the game log the whole allowlist, by name. Crafty's two logs stay on the host; the server folder's `logs/`, like its `whitelist.json`, goes into the archive taken at the next stop.

Java changes use the server's `whitelist add/remove` command. This operator interface accepts 3–16 ASCII letters, digits, and underscores for Java names. Bedrock changes use Floodgate's `fwhitelist add/remove` command with the gamertag, without the configured Floodgate username prefix. The [Floodgate documentation](https://geysermc.org/wiki/floodgate/features/) defines that command routing.

For Bedrock, this interface accepts Unicode letters/numbers, ASCII spaces, and underscores, with no leading/trailing spaces and at most 16 UTF-16 units. Tags containing spaces are passed as one quoted argument. Quotes, backslashes, control characters, and command punctuation are rejected. Floodgate build 141's [argument parser](https://github.com/GeyserMC/Floodgate/blob/81b65ccb766bf8024858ebf3eefa6974056aecc5/core/src/main/java/org/geysermc/floodgate/player/audience/PlayerAudienceArgument.java) supports quoted names and uses the same length boundary. Its source is unchanged from build 140; build 141 changes only the cloud command-framework dependency, from 2.0.0-beta.16 to 2.0.1. Passing this syntax check does not verify an Xbox account or its UUID.

The operation reads the server's `whitelist.json` before sending a command. If the supplied UUID already has the requested membership, it returns `allowlist: unchanged` without sending anything. Otherwise it sends one command and polls `whitelist.json` for up to 60 seconds until that exact UUID is present for add, or absent for remove. It reports `allowlist: updated` only after observing the requested membership. Invalid or duplicate UUID entries prevent verified completion.

Floodgate's [whitelist implementation](https://github.com/GeyserMC/Floodgate/blob/81b65ccb766bf8024858ebf3eefa6974056aecc5/core/src/main/java/org/geysermc/floodgate/command/WhitelistCommand.java) can resolve gamertags asynchronously, and Crafty's API answers only that it passed the line to the console, so only the file establishes completion. A lookup failure, missing change, or mismatched UUID reaches a bounded failure. A command may have changed access or may still be completing when verification fails; inspect private server state and correct the identity or lookup problem before retrying. Repeating the same request verifies current state and avoids repeating a completed change.

A Java account that was renamed, or deleted, no longer resolves to a UUID, though the allowlist may still hold it under its old name. For a Java removal only, the player file may hold the name alone, `{"name": "<JavaName>"}`. The adapter then removes the one entry with that name, ignoring case, by rewriting `whitelist.json` (same owner and mode, synced to disk with its folder) and sending `whitelist reload` and `whitelist list`. Crafty's answer shows only that the lines reached the server, so the adapter reads the server's `logs/latest.log` from where it ended before the reload and waits up to 60 seconds for the game's own lines: `Reloaded the whitelist`, then a list without the name. It answers `updated` once that list lacks the name and the file still does. A server that does not answer in time, or still lists the name, fails the change, and so does a log that can no longer be read after the rewrite; a retry is safe. The adapter refuses, changing nothing, when it cannot read the server log before it starts, when the file changed since it was read, as when someone used the Crafty console meanwhile, and when more than one entry has the name. When no entry has the name it still reloads and checks the list the same way, so a retry finishes a removal whose reload never reached the server, and answers `allowlist: not-listed`. The check before the rename cannot be atomic with it, because the game keeps no lock the adapter could share: a whitelist command typed into the Crafty console in the instant between the two is lost, so avoid console allowlist edits while a removal by name runs. The launcher sends a name alone only when Mojang does not know the name.

Successful output contains only the instance ID, edition, operation, and `updated`, `unchanged` or `not-listed` result. Failures print one fixed diagnostic as `{"error": ...}`. UUIDs, names, console responses, and allowlist contents never reach the output. These commands do not disable the allowlist, change online authentication or assign operator privileges; the adapter's separate `operator` action does that ([launcher](launcher.md#operators)). Access removal changes allowlist membership; it does not promise immediate disconnection of an already-connected player.

`tests/test_minecraft_access.py` exercises the shared module through a controlled console and private-file boundary: routing, quoted Unicode Bedrock tags, eventual completion, duplicate operations, exact UUID matching, failed lookup/removal, malformed files, private-output handling, and command-injection rejection. `tests/test_minecraft_crafty.py` runs the adapter's action against a fake Crafty API and server folder, including the removal by name, the player file's checks and the command line the launcher sends. These fixtures use made-up players, and do not contact identity services or connect family devices.
