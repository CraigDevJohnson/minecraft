# ADR 0006: The family server is operated from the cloud

Status: Accepted, 2026-10-12. Supersedes part of [ADR 0005](0005-lobby-launcher-starts-from-aws.md) (the Launcher "can never stop the host") and part of [ADR 0002](0002-dynamic-public-ipv4-with-cloudflare-hostname.md) (an ordinary stop parks the hostname from the operator computer).

On October 12, 2026, Craig ruled out running any Minecraft procedure on his Mac: "I do not want this running playbooks or anything at all locally on my Mac. It needs to be setup to call via the /Minecraft button, and some other local call, but not run locally." That morning's stop had waited over an hour on a permission prompt on the Mac while the archive itself was done in eighteen minutes, and every deploy of this repository still ran from a checkout that had fallen behind `main`. The Launcher ([ADR 0005](0005-lobby-launcher-starts-from-aws.md)) already starts the host from AWS and holds everything a stop needs: Run Command to the host, the Cloudflare token, the state parameter, the alarm and the signed route the site calls.

## Decision

- **One operator, in AWS.** The Launcher function is the only thing that starts, stops and allowlists the server. Every entry point sends it one signed request: the `/minecraft` page, the **Server control** GitHub Actions workflow, and the `task server:*` targets from any terminal with an AWS profile. Nothing runs where the request is made.
- **Stop.** `POST /server/stop` drains the host the way the workstation `stop` did, through the host adapter's `host-drain` and `host-status` actions over SSM, then stops EC2 and parks the hostname on `192.0.2.1`. The request answers at once and a follow-up run finishes the work, handing the rest to a fresh run when a Lambda run ends first; the whole stop has one 75-minute deadline. Without `{"force": true}` a stop is refused while players are online, or while the game does not answer and the count is unknown; the launcher accepts `force` only from an operator, never from a site's role, so the page cannot send it and the workflow's checkbox can. The function's role, and the administrator-created launcher boundary, gain `ec2:StopInstances` on this one host.
- **Allowlist.** `POST /server/allowlist` looks the player up (Mojang for a Java name, GeyserMC's XUID lookup for a Bedrock gamertag, from which the Floodgate UUID follows), then runs the adapter's `allowlist` action on the running server with the verified identity in a private temporary file. The launcher refuses it to the sites' roles, so only an operator (the workflow, or the Task target with an administrator's profile) can change who may join.
- **The idle stop stands aside** while a Launcher stop is under way for the current launch, so the two never drain the host at once. The reverse already held: the Launcher reports the idle stop's drain as `stopping`.
- **A second OIDC role.** `minecraft-server-control` trusts only the repository's `server` GitHub Environment and may only invoke the Launcher's functions. The Launcher's Function URL admits it beside the sites' roles through the `control_role_arn` input.
- **Deploys from GitHub Actions** (issue #59). The **Deploy** workflow runs only when Craig starts it, to plan or to apply. Its one job runs in the `deploy` GitHub Environment, which only `main` may use, and assumes `minecraft-operator` through OIDC; the operator role's trust gains that one statement. Every run holds the operator's write credentials, so no push starts one: Craig starts a plan run, reads the plan it posts, then starts an apply run, because GitHub offers a required reviewer on a private repository only with GitHub Enterprise. The private inputs are environment secrets the workflow writes to files it never prints; the plan summary shows resource changes only. The root accepts the packages through `package_dir` and leaves the provider's `assume_role` out when `operator_role_arn` is unset, because the runner already is the operator.

## Consequences

- No step of starting, stopping, allowlisting or deploying runs on a workstation. `scripts/minecraft_host.py` and the host runbooks remain for restoring a world from an archive, the Crafty console over an SSM port-forward, and a hands-on emergency.
- The private `users.json` on the operator computer is no longer part of any procedure: the server's own whitelist is the record, and each workflow run prints what it changed.
- The operator role can now be assumed from GitHub, only by a Deploy run on `main` that Craig started by hand; the job checks that his own account started the run and any re-run of it. That and the control role are created by hand from committed JSON, like the health role (aws-setup `aws-design.md` §13).
- A stop that fails or runs past its deadline is recorded as `stop-failed`, counted as `StopFailures` on the existing alarm, and leaves the host as it is, so a later stop can drain it again. The status then follows what the host is really doing.
- Rejected: moving the Python runbook onto a GitHub runner (a copy of the Cloudflare token in a GitHub secret, the whole drain on a runner holding the operator role, and still nothing for the page to call), and letting the host stop itself (`ec2:StopInstances` on its own instance profile and the token on the internet-facing host, which the design keeps off it on purpose).
