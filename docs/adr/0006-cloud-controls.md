# ADR 0006: The family server is operated from the cloud

Status: Accepted, 2026-10-12. Supersedes part of [ADR 0005](0005-lobby-launcher-starts-from-aws.md) (the Launcher "can never stop the host") and part of [ADR 0002](0002-dynamic-public-ipv4-with-cloudflare-hostname.md) (an ordinary stop parks the hostname from the operator computer). Amended 2026-10-12: the repository is public, so the `deploy` environment has Craig as its required reviewer. Amended 2026-10-17: restores run through the Launcher (#61), the Crafty console runs in a Session Manager shell from the AWS console instead of a port-forward (#62), and the Launcher's rare overlaps with the idle stop and with itself stay documented (#64).

On October 12, 2026, Craig ruled out running any Minecraft procedure on his Mac: "I do not want this running playbooks or anything at all locally on my Mac. It needs to be setup to call via the /Minecraft button, and some other local call, but not run locally." That morning's stop had waited over an hour on a permission prompt on the Mac while the archive itself was done in eighteen minutes, and every deploy of this repository still ran from a checkout that had fallen behind `main`. The Launcher ([ADR 0005](0005-lobby-launcher-starts-from-aws.md)) already starts the host from AWS and holds everything a stop needs: Run Command to the host, the Cloudflare token, the state parameter, the alarm and the signed route the site calls.

## Decision

- **One operator, in AWS.** The Launcher function is the only thing that starts, stops, restores and allowlists the server. Every entry point sends it one signed request: the `/minecraft` page, the **Server control** GitHub Actions workflow, and the `task server:*` targets from any terminal with an AWS profile. Nothing runs where the request is made.
- **Stop.** `POST /server/stop` drains the host the way the workstation `stop` did, through the host adapter's `host-drain` and `host-status` actions over SSM, then stops EC2 and parks the hostname on `192.0.2.1`. The request answers at once and a follow-up run finishes the work, handing the rest to a fresh run when a Lambda run ends first; the whole stop has one 75-minute deadline. Without `{"force": true}` a stop is refused while players are online, or while the game does not answer and the count is unknown; the launcher accepts `force` only from an operator, never from a site's role, so the page cannot send it and the workflow's checkbox can. The function's role, and the administrator-created launcher boundary, gain `ec2:StopInstances` on this one host.
- **Allowlist.** `POST /server/allowlist` looks the player up (Mojang for a Java name, GeyserMC's XUID lookup for a Bedrock gamertag, from which the Floodgate UUID follows), then runs the adapter's `allowlist` action on the running server with the verified identity in a private temporary file. The launcher refuses it to the sites' roles, so only an operator (the workflow, or the Task target with an administrator's profile) can change who may join.
- **Restore** (2026-10-17, #61). `POST /server/restore` with an archive's name puts that archive back in place of a stopped server's world, then starts the game. Only an operator may ask, never a site's role. The Launcher records the restore (phase `restoring`, shown as `starting`, because the page knows no other state), starts the host, points the hostname, and runs the host adapter's existing `restore` action over SSM, which checks the archive's SHA-256 before it swaps anything. Once the archive is in place, a fresh start's record takes over and starts the game. The restore has one 45-minute deadline and hands off to a fresh run like the stop. The function's role needs nothing new: the host role already reads the archives, and Craig finds the name in the S3 console. The Server control workflow gains a `restore` action and `task server:restore` the same request.
- **The console in a browser shell** (2026-10-17, #62). Nothing forwards Crafty's port. The adapter's new `console` action sends one console line through Crafty's loopback API and prints what the server logged in the next 3 seconds, and `setup-api-key` creates the adapter's own API key on a freshly installed Crafty. Both run in a Session Manager shell Craig opens from the AWS console in a browser, signed in as `WorkloadsAdmin`.
- **The idle stop stands aside** while a Launcher stop or restore is under way for the current launch, so it does not begin a drain of its own. The reverse already held: the Launcher reports the idle stop's drain as `stopping`. The records live in SSM parameters, which have no conditional write, so two windows of a second or less remain: a Member's Stop landing between the idle stop's read and its own save lets both begin a drain (one fails at once, with a spurious alarm), and a Member's Start landing between a stop's last read and last write is lost (the host runs without the game until a forced stop, and the alarm fires). A Start landing on a restore's request can likewise replace it. Craig chose to leave these documented over a DynamoDB record with conditional writes (#64, 2026-10-17); see the [launcher runbook](../operations/launcher.md#rare-overlaps).
- **A second OIDC role.** `minecraft-server-control` trusts only the repository's `server` GitHub Environment and may only invoke the Launcher's functions. The Launcher's Function URL admits it beside the sites' roles through the `control_role_arn` input.
- **Deploys from GitHub Actions** (issue #59). The **Deploy** workflow runs only when Craig starts it, to plan or to apply. Its one job runs in the `deploy` GitHub Environment, which only `main` may use, and assumes `minecraft-operator` through OIDC; the operator role's trust gains that one statement. Every run holds the operator's write credentials, so no push starts one: Craig starts a plan run, reads the plan it posts, then starts an apply run with that plan's digest, and the `deploy` environment names Craig as its required reviewer, so GitHub holds each run until he approves it. The apply run plans again and applies only a plan with that digest, so it applies exactly what he read or nothing. No other workflow may name the `deploy` environment, because the role trusts a job by its environment. The private inputs are environment secrets the workflow writes to files it never prints, with their quoted values masked in the log; the plan summary shows resource changes only. The root accepts the packages through `package_dir` and leaves the provider's `assume_role` out when `operator_role_arn` is unset, because the runner already is the operator.

## Consequences

- No step of starting, stopping, restoring, allowlisting or deploying runs on a workstation, and nothing forwards a port to one. The Crafty console and a hands-on emergency use a Session Manager shell opened from the AWS console; `scripts/minecraft_host.py` and the host runbooks remain only for an emergency the Launcher cannot reach. The operator role keeps its port-forwarding permission, which the opt-in on-demand host mode ([ADR 0003](0003-on-demand-host-sessions.md)) still uses.
- The private `users.json` on the operator computer is no longer part of any procedure: the server's own whitelist is the record, and each workflow run prints what it changed.
- The operator role can now be assumed from GitHub, only by a Deploy run on `main` that Craig started by hand and approved as the `deploy` environment's reviewer; the job checks that his own account started the run and any re-run of it. That and the control role are created by hand from committed JSON, like the health role (aws-setup `aws-design.md` §13).
- A stop that fails or runs past its deadline is recorded as `stop-failed`, counted as `StopFailures` on the existing alarm, and leaves the host as it is, so a later stop can drain it again. The status then follows what the host is really doing.
- Rejected: moving the Python runbook onto a GitHub runner (a copy of the Cloudflare token in a GitHub secret, the whole drain on a runner holding the operator role, and still nothing for the page to call), and letting the host stop itself (`ec2:StopInstances` on its own instance profile and the token on the internet-facing host, which the design keeps off it on purpose).
