# ADR 0009: One host per world

Status: Accepted, 2026-11-10. Supersedes [ADR 0004](0004-crafty-multiverse-rebuild.md)'s Multiverse worlds and, for the world hosts, its retained data disk. Built and checked offline; nothing is live until the first Deploy and the proof run in the [worlds runbook](../operations/worlds.md). Amended 2026-11-11: the retirement pull request (refs #88) removed the family host, its data disk and its two old state parameters from the configuration; the Deploy in the [worlds runbook](../operations/worlds.md#the-family-hosts-retirement) retires them.

[ADR 0004](0004-crafty-multiverse-rebuild.md) put `survival` and `creative` in one Paper server as Multiverse worlds. Paper loads its plugins for the whole server, so a mod added for one world ran in every world, and a bad one took every world down. The one host also ran, and billed, whichever world was being played. On November 10, 2026, Craig chose to give each world a host of its own, with its own mods, and to start every world fresh.

## Decision

- **One host per world.** [`runtime/crafty/server.json`](../../runtime/crafty/server.json) lists the worlds, `survival`, `creative` and `adventure`, and OpenTofu makes one EC2 host for each id (`infra/worlds.tf`). Each host is a copy of the lifecycle ADR 0004 built: Crafty in Docker, one Paper server with Geyser and Floodgate, Java on 25565, Bedrock on 19132 and 19133, a start, a stop that stores an archive, and the idle stop. Each world has its own address, `<world>.<the public hostname>`, and worlds start and stop independently. There is no Multiverse and no portal: a player changes world by joining another address.
- **The world lives on the host's root disk.** `/srv/minecraft` is a plain folder on the host's encrypted 20 GiB root disk. A world host has no data disk. The archive stored in S3 at every stop, under `instances/<world>/crafty/`, is the recovery point.
- **A host sets itself up.** The host's user data (`scripts/world-bootstrap.sh.tftpl`) installs Docker, the AWS CLI, the folders, the `minecraft-instance` wrapper and `minecraft-crafty.service`, writes the operator configuration, and powers the host off. It holds nothing from `server.json`. At the world's first start the adapter the Launcher carries does the rest: it brings Crafty up, makes its API key, creates the server from the pinned content, and restores the newest archive with a SHA-256 beside it when S3 holds one. With no archive it keeps the fresh world. With objects under the world's prefix but no verified archive it fails instead of starting a fresh world over them. A marker written last (`crafty/state/<world>-provisioned`) ends the set-up, and each step checks before it acts, so a start that ran out of time is carried on by the next.
- **Mods are pinned and switched per world.** A mod is a Paper plugin in the manifest's `mods` catalog, pinned by URL and SHA-256 like every jar. Each world lists the mods it may run, each on or off by default. A switch away from the default is kept in one parameter, `/<prefix>/launcher/mods`, and applies at that world's next start: the start command names the mods that are on, and the adapter removes every other jar directly in `plugins/`. Only ids the manifest lists for a world are ever sent, so a switch can only choose among pins. The site offers the switches to Members with its `minecraft-admin` grant; `minecraft` Members start and stop worlds.
- **One allowlist of record.** The family's allowlist is one parameter, `/<prefix>/launcher/allowlist`, changed only through the operator's allowlist route. Every start carries it to the host, where the adapter writes it over the stopped server's `whitelist.json`, so a restored archive never brings a removed player back. A change also reaches each world that is running.
- **Nobody is an operator in game.** No runbook step ops an account, a fresh world has no operators, and a mod that needs permissions ships them in a managed file (FastAsyncWorldEdit's `permissions.yml`). Console commands go through the adapter's `console` action in a Session Manager shell.
- **The family host stays as it is for now.** `aws_instance.host`, its data disk and its bootstrap stay declared and untouched, and the new Launcher never starts, stops or reads the family host. A later pull request retires it ([worlds](../operations/worlds.md#the-family-hosts-retirement)).

## Consequences

- Only the worlds being played run. A stopped world host costs its 20 GiB root disk, about $1.60 a month; three hosts running at once cost three hosts' compute.
- A mod, a crash or a restart touches one world. Inventories, claims and plugin data are separate per world, because each world is its own server.
- Every Deploy runs with all worlds stopped. An apply replaces the functions under any start or stop in flight, and an apply that replaces a host ends a game on it. A stop first means every world's play is in an archive before anything changes.
- A change to `scripts/world-bootstrap.sh.tftpl` or `scripts/install_aws_cli.sh` replaces every world host on the next apply. That is safe only because each stopped world's archive is in S3: the new host restores the newest one at the world's next start. Crafty's own login, API key and settings are made again, and whatever a restore set aside in `crafty/staging` is gone.
- A change to `server.json` replaces nothing. It reaches a world at its next start ([ADR 0008](0008-the-adapter-applies-the-pinned-server-content.md)). Adding a world there adds a host, its parameters and its idle-stop target at the next Deploy.
- The world hosts and the family host share one instance role. Its S3 statements cover every world's prefix, so any world host can read, write and delete another world's archives. Splitting the role per world was not worth it for one family's servers; the mods are pinned and reviewed, and the bucket is versioned.
- The dev and production Launchers drive the same real worlds. They share the hosts, each world's record, the mods switches and the allowlist, so a start or a switch from the dev site is real. The two shared parameters have no lock: two changes in the same instant can lose one.
- The allowlist of record is one standard String parameter, 4 KB, which is room for roughly 40 players. Names sit in Parameter Store in plain text and are never logged.
- A world's first start does more than a later one: the image pull, the downloads, the import and perhaps a restore. It may outlast the Launcher's 15-minute start deadline and read `failed`; a second Start carries on where the first stopped.
- The worlds are fresh. Nothing moves from the family server's `survival` and `creative`, whose archives stay under `instances/family/crafty/`, and every player is added again once through the allowlist action.
- Each world's server keeps its own NetherNet identity, so a Bedrock player accepts the trust prompt once per world.
- The first Deploy needs three DNS A records made by hand, because the Launcher only ever updates an existing record ([worlds](../operations/worlds.md#the-first-deploy)).
- Until the family host is retired its stopped host, root disk and data disk keep billing as before, and the pinned content no longer describes it: the manifest has no `family` world. The host keeps the adapter and content its last start installed, and only the emergency host commands, removed with it by the retirement pull request, could still start it.
- Going back means reverting the pull request and deploying. The plan then destroys the world hosts and their parameters, the family host is as it was, and the worlds' archives stay in S3.
- Rejected: per-world plugin loading inside one Paper server, which Paper does not offer; a proxy in front of several servers on one host, which keeps every world's cost and failure tied together; and a data disk per world, which bills while the world is off and needs the by-hand disk set-up for every new world.
