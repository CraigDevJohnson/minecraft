# ADR 0008: The adapter applies the pinned server content

Status: Accepted, 2026-10-16. Builds the NetherNet design Craig approved on 2026-10-03 (#26, #30) on the Crafty host.

[`runtime/crafty/server.json`](../../runtime/crafty/server.json) pins the Crafty image, every server jar and Geyser's configuration, but it reached the server only once: `stage-import` built the folder Crafty imported on 2026-10-10. Nothing applied a later change, so a new Geyser pin or the NetherNet configuration would have needed hands on the host, which [ADR 0006](0006-cloud-controls.md) rules out. Bedrock 26.60 drops RakNet, so the family server must offer NetherNet before it reaches the family's devices (#26). NetherNet also needs two more published ports and the host's public address in Geyser's answers, and that address changes on every EC2 start ([ADR 0002](0002-dynamic-public-ipv4-with-cloudflare-hostname.md)).

## Decision

- **The launcher carries the manifest.** `server.json` joins the adapter files of [ADR 0007](0007-the-launcher-carries-the-host-adapter.md): the launcher package holds it, and every start installs it as `/opt/minecraft-crafty/scripts/server.json` with the same checks as the adapter. A Deploy therefore brings a content change to the host at the next start.
- **Each start applies it while the game is stopped.** Before asking Crafty to start the server, `minecraft-instance start` brings the stopped server to the manifest, in this order. A start of a server that is already running changes nothing.
  1. **Address.** With both transports selected, it reads the host's public IPv4 from IMDSv2. A failed lookup fails the start before anything changes.
  2. **Files.** Each jar whose SHA-256 differs is downloaded into root's `crafty/staging` and checked before any file in the server folder changes. Each changed jar and managed file is then written beside its name, checked against its SHA-256, and renamed into place. It gets the owner and mode of the file it replaces, or of its folder for a new file. Every step goes through folder descriptors that never follow a link, because Crafty's account can write in the server folder. Jars an earlier manifest pinned and this one does not are removed. `crafty/state/<instance>-content.json` records which jars were applied.
  3. **A new Paper waits for an archive.** Paper upgrades the world on its first start, so a manifest that changes `paper.jar` is applied only when the server folder is exactly as its last archive stored it. Otherwise the start fails and says to stop the server once, which stores that archive. Paper goes in first, so a later failure in the same start never leaves an unarchived new Paper behind.
  4. **Compose.** It renders `/opt/minecraft-crafty/compose.yaml` from the manifest. That means the Crafty image by digest, Java TCP 25565 and RakNet UDP 19132, plus signaling TCP 19132 and WebRTC UDP 19133 when both transports are selected, and the web UI on loopback only. A changed file is written, and `docker compose up --wait` recreates Crafty's container. If Docker cannot bring Crafty up with it, the previous file goes back and the start fails. A server that Crafty started meanwhile fails the start too.
  5. **Launch command.** Through Crafty's API it sets the server's launch command to carry `-DgeyserAdvertiseAddresses=<public IPv4>` before `-jar`, or no such flag for RakNet alone. It then reads the command back. A launch command without exactly one ` -jar ` fails the start.
- **Only the approved Geyser configurations load.** The adapter accepts a manifest whose managed Geyser configuration is exactly one of the two that #30 approved. The first is RakNet alone. The second, `both`, adds built-in signaling on TCP 19132 and WebRTC on UDP 19133, with the trust-on-first-use prompt and no TLS or external signaling service.
- **The family server selects both.** This change moves the managed configuration to `both` (SHA-256 `961fc91c79c38f8e09fd14d1e959b06522ec72b595b933e78fef83563e4b8e42`). It keeps the pinned Geyser 2.11.3 build 1247, which already has both transports. A Geyser build that supports 26.60 is a later pin change that the same path applies.
- **The installer uses the same rendering.** `scripts/install_crafty.sh` writes `compose.yaml` with `minecraft_crafty.py render-compose`. For the RakNet manifest it writes the same bytes the installer wrote before. It installs `server.json` beside the adapter, where each start reads it.
- **The health check asks for signaling.** When the checked-out manifest selects both transports, the Minecraft health workflow also asks the signaling endpoint on TCP 19132 for its discovery answer with one `GET /v1/join`. It requires a bounded JSON answer that says Xbox sign-in is required ([unattended health](../operations/unattended-health.md)).

## Consequences

- Players keep the address they have. Bedrock players still add `mc.craigdevjohnson.com` on port 19132; a client that speaks NetherNet asks the signaling endpoint on that port and is shown the trust prompt once. Java is unchanged.
- The private infrastructure input `bedrock_transport` must be `"both"` (the OpenTofu default) for the security group to admit TCP 19132 and UDP 19133 and to allow ICE checks out. The Crafty runbook had the deployment inputs set `"raknet"` until this change.
- Geyser keeps its NetherNet identity in `plugins/Geyser-Spigot/nethernet/` in the server folder. It is in every archive and comes back with every restore, so a restore never makes players trust the server again. Deleting that folder does.
- The first start after the Deploy rewrites one file, recreates Crafty's container and changes the launch command. Every later start reads the host's address and changes only the launch command, when the address changed.
- A Paper change needs one Launcher stop before the start that applies it, if anything ran since the last archive. Rolling Paper back to an older version needs the archive from before the upgrade restored first, because Paper does not load a world a newer Paper saved. Jar downloads come from the pinned hosts over the existing HTTPS egress.
- The install lines each start and allowlist command carries grow from about 31 KiB to about 39 KiB, and the Go test still keeps them under 48 KiB.
- Not yet proven live: the container loading Geyser's WebRTC natives on the host, Docker's UDP publishing for ICE, and a Bedrock client joining over NetherNet. Craig's first start after the Deploy, followed by the health workflow, is that proof.
- Rejected: applying content from the Deploy workflow, because a stopped host cannot take it and it would need Run Command from GitHub. Also rejected: a separate SSM document, because it is one more thing to keep in step, and syncing a running server, because Paper and plugins read their jars only at start.
